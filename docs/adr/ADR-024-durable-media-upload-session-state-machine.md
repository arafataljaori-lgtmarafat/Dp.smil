# ADR-024: آلة حالات دائمة لجلسة رفع الوسائط

## السياق

لا يستطيع تدفق الرفع العابر وحده تمثيل علاقة التخزين وقاعدة البيانات عند عطل العملية أو إعادة المحاولة أو تنفيذ عامل تسوية. يلزم سجل دائم، محكوم بالملكية والحالة، قبل إضافة الاستيعاب المتدفق في Phase 3B.

## القرار

يضاف نموذج `MediaUploadSession` مملوك بالمستخدم ومقيد بالحالة، وبآلة الحالات `created → processing → committed|failed|expired`. ينفذ PostgreSQL شكلاً صالحًا لكل حالة عبر قيد CHECK، ويربط `(ownerUserId, caseId)` بالحالة وبـ `committedMediaId` المحتمل عبر مفاتيح خارجية مركبة. الإنشاء إديمبوتنسي ضمن `(ownerUserId, caseId, idempotencyKey)` باستخدام `INSERT ... ON CONFLICT DO NOTHING RETURNING` ثم قراءة آمنة للسجل الموجود.

## السبب

تمنع القيود الدائمة صفوفًا منطقية مستحيلة حتى عند تجاوز الخدمة. يُنشأ `processingToken` من الخادم عند المطالبة بالمعالجة؛ كل انتقال نهائي من `processing` يقارن الرمز والحالة ضمن شرط UPDATE الذري، فلا يمكن لطلب قديم أن يلتزم بعد انتهاء الجلسة أو فشلها.

## النتائج

لا يخزن النموذج أسرار مصادقة أو جلسات مستخدم صريحة. يحتفظ بسجل هدف الخادم (`targetMediaId` و`targetStorageKey`) للحالة الجارية فقط، ويفصل كائن التدريج عن `MediaAsset` الملتزم. يوفر المستودع عمليات محددة للإنشاء/القراءة/المطالبة/الالتزام/الفشل/الانتهاء/تعداد الجلسات القديمة، ولا يوفّر تحديثًا عامًا للحالة.

## البدائل المدروسة

رُفض قفل ذاكرة داخل عملية واحدة لأنه لا يصحح سباقات عمليات متعددة أو عامل تسوية. ورُفض وضع حالة الرفع داخل كائن التخزين أو العميل لأنه لا يوفر رسم ملكية PostgreSQL أو انتقالات قابلة للتدقيق والاسترداد.
