# ADR-017 — PostgreSQL Personal Graph Integrity

**الحالة:** مقبول ونشط.

## السياق

DentPilot Smile Studio تطبيق شخصي يملك فيه المستخدم كل حالة ووسيط ومشروع ووظيفة توليد ونسخة وسجل تدقيق عبر `ownerUserId`. كانت القيود السابقة تمنع خلط مستخدمين مختلفين، لكن المراجعة الهندسية أثبتت حاجتنا لمنع الرسوم المتناقضة داخل المستخدم نفسه، مثل مصدر من حالة أخرى أو مشروع/وظيفة لا ينتميان إلى حالة التدقيق نفسها.

## القرار

تفرض PostgreSQL الرسم التشغيلي الشخصي، وليس التطبيق فقط. تستخدم قاعدة البيانات مفاتيح مرشحة ومفاتيح أجنبية مركبة لفرض ما يلي:

| العلاقة | القيد النشط |
|---|---|
| lineage الوسيط | `(ownerUserId, caseId, sourceMediaId) → (ownerUserId, caseId, id)`؛ لذلك يبقى المصدر داخل الحالة نفسها. |
| مصدر المشروع | المشروع والمصدر داخل المستخدم والحالة نفسيهما. |
| وظيفة التوليد | المشروع والحالة والمصدر يمثلون رسمًا واحدًا. |
| إصدار التوليد | المصدر والمخرج والوظيفة والحالة والمشروع داخل lineage واحد. |
| سجل التدقيق | الحدث الحاوي مشروعًا يجب أن يحمل الحالة المطابقة؛ والحدث الحاوي وظيفة يجب أن يحمل الحالة والمشروع المطابقين للوظيفة. |

يبقى حدث تدقيق الحالة فقط مشروعًا مثل `CaseCreated` صالحًا. تفرض CHECK presence rules أن المشروع لا يظهر بلا حالة وأن الوظيفة لا تظهر بلا حالة ومشروع.

## سبب القرار

قد تنشئ أدوات الاستيراد أو التشغيل الإداري أو خطأ مستقبلي في طبقة التطبيق معرّفات صحيحة منفردة لكنها متناقضة منطقيًا. تجعل القيود العلائقية هذه الحالات مستحيلة بنيويًا. تخضع الترحيلات إلى تحقق مسبق وفشل مغلق إذا اكتشفت بيانات تاريخية متعارضة، ولا تستخدم triggers.

## النتائج

يجب أن تمثل Prisma المفاتيح والعلاقات المركبة المدعومة كي يبقى فحص الانجراف خاليًا من الاختلاف. تتحقق CI من سلسلة الترحيلات على PostgreSQL جديدة، و`prisma validate`، وفحص الانجراف، واختبارات التكامل الإلزامية. لا يعد هذا القرار ميزات منتج أو مصادقة أو توسعًا نحو Phase 2.

## البدائل المدروسة

رُفض التحقق في TypeScript فقط لأنه لا يحمي من الإدخال المباشر أو أدوات الإدارة. ورُفضت triggers لأن المفاتيح المركبة وCHECK تعبر عن القواعد المطلوبة مباشرة وبصورة شفافة وقابلة للتدقيق.
