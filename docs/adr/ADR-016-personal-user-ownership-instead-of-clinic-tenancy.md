# ADR-016 — ملكية المستخدم الشخصية بدل tenancy العيادة

**الحالة:** مقبول ومطبق قبل Phase 2.  
**التاريخ:** 2026-08-26.

## السياق

افترضت البنية الأولى خطأً أن DentPilot Smile Studio مساحة عمل عيادة متعددة الموظفين. أدى ذلك إلى `Clinic` و`ClinicMembership` وأدوار عيادة وحقل `clinicId` في كل كيان تشغيلي. نموذج المنتج المصحح هو تطبيق تجاري شخصي مشابه لاستخدام تطبيق إنشاء محتوى بصري: ينشئ المستخدم حسابًا شخصيًا ثم ينشئ حالات ومشروعات ويرفع الوسائط وينتج النتائج ويحفظها أو يشاركها.

## القرار

أزيلت مفاهيم العيادة والعضوية والأدوار من المنتج النشط. أصبح `ownerUserId` حقل الملكية الوحيد للبيانات التشغيلية، وتستخدم جميع الطبقات — PostgreSQL وPrisma والمجال والتطبيق والطابور وAPI والاختبارات — الاسم نفسه. تفرض قاعدة البيانات المراجع المركبة `(ownerUserId, parentId) → (ownerUserId, id)` لحماية كل علاقة بين كيانات شخصية.

يحمل سياق التطوير حساب مستخدم واحدًا مركزيًا إلى حين المصادقة في Phase 2. يحمل العامل ممثل نظام تقنيًا، لكنه يعمل دائمًا تحت `ownerUserId` الصريح في رسالة الطابور ولا يملك سياق مستخدم عالميًا.

## النتائج

تُرحل البيانات التطويرية فقط عندما يكون لكل عيادة سابقة membership واحدة تمامًا؛ يفشل الترحيل مغلقًا عند غموض الملكية. حذفت الجداول والقيود القديمة بعد backfill وإعادة بناء قيود المستخدم. تحافظ الإديمبوتنسية والإثبات وسلامة المصدر والتنظيف التعويضي على سلوكها؛ تغير نطاقها من العيادة إلى المستخدم.

لا تمنع هذه البنية إضافة branding اختياري في ملف المستخدم، مثل اسم الطبيب أو اسم الممارسة أو الشعار أو التخصص. تلك البيانات لا تنشئ team tenancy أو إدارة ممارسة أو أدوار موظفين. إذا احتاج المنتج حسابات فريق مستقبلًا، فسيصمم ذلك كنموذج جديد صريح لا كإرث مخفي في نموذج المستخدم الشخصي.
